# Gallery design

The gallery is a standalone example and a native review surface for the public components and icons. It must remain runnable without any consumer application.

## Separation from the library

The [entry point](../../source/examples/gallery/main.go) owns application startup, appearance selection and shutdown. The [internal gallery](../../source/examples/gallery/internal/gallery/gallery.go) uses the `shells/sidebar` style and owns demonstration content and in-memory state. Neither is part of the public component API.

Examples should demonstrate ordinary consumer integration, not introduce gallery-only behavior into components. The entry point places application data in `~/.oneo/onevra`. The gallery restores window size and position, sidebar width and expansion state, and the selected navigation item from `state.yaml`, and saves them on normal window close or application quit. Selection uses named routes rather than catalog indices; unknown routes and unreadable state fall back to defaults. Restored windows are kept within a connected display's work area where minimum sizes allow. Interactive demo values stay in memory, and no user content is persisted. Only the YAML filenames are read; existing JSON files can be renamed to `.yaml` to retain their values, since JSON syntax is valid YAML. Application preferences live separately in `config.yaml`, shared by the sidebar theme menu and the settings dialog. The theme defaults to System; menu choices apply immediately and are saved immediately. An explicit `-theme` launch argument temporarily overrides the saved preference without rewriting it. Missing or invalid configuration falls back to System, with read and save errors logged. The disk-free `Gallery.New` path keeps component examples and native tests isolated from real user settings. The first launch of each application version presents a simple, standalone welcome entrance as a full-window Shell replacement page without sidebar navigation. Enter gallery restores the main interface with its saved navigation and sidebar state. The shown version is saved immediately in `state.yaml`; subsequent launches of that version skip the entrance, while a version mismatch or missing record shows it again. Save failures are logged and may cause the entrance to reappear. The gallery's application version is kept aligned with `packer.yaml` by a regression test and must be updated alongside packaging versions. The disk-free startup always shows the entrance for review. Overview retains a separate Welcome page with interactive primary-component samples isolated from the individual demonstrations; the startup entrance does not build or share those samples. Its grouped sidebar keeps the complete navigation catalog visible. It navigates between Onevra demonstrations, a Lucide icon library with icon-only outline buttons that copy their names and MyGo's remaining built-in widgets. Plugins follow the icon library; component pages share flat, purpose-based groups regardless of implementation, with a trailing dot marking built-in MyGo entries; Plugins have no dot. Public `components` demonstrations keep state isolated between examples and from the upstream catalog. Component review pages use a continuous, viewport-wide pixel grid behind the header, examples and empty space, rather than individually framed grid containers. Settings → Appearance can disable this background immediately and persist the preference without changing the PixelGrid component demonstration. The grid stays fixed while examples scroll; the Welcome page and Terminal retain their dedicated backgrounds. Markdown keeps the page grid and titlebar while its body renders the document without an extra example heading. Preview layout follows the component: Text and Collapsible variants stack with muted, regular-weight descriptions; NativeSelect has its own section below the custom Select variants; other component variants wrap horizontally beneath their headings. Rows remain appropriate inside a component, such as a radio group or tab list. Onevra previews do not include disabled-state demonstrations; disabled behavior remains covered by automated tests. MyGo entries are grouped by type and open separate control-only pages, without source listings or tutorial prose. State and usage variants remain interactive where enabled, with independent in-memory state per page and variant. The upstream examples omit direct-use primitives and native menus, as well as components recorded as replaced or excluded in the [component decisions](../../source/examples/gallery/internal/gallery/mygo_review.go); supporting controls use Onevra equivalents where available. Unstyled Base APIs remain building blocks rather than a duplicate widget catalog. The exhaustive icon catalog is generated alongside the Lucide assets by [lucidegen](../build.md#updating-lucide-icons). It belongs only to the gallery and references public named accessors; ordinary library consumers retain no runtime registry. Onevra's GridView uses MyGo virtualization to build visible icons on demand. The Shell demonstration also shows sample icons at multiple sizes and inherited text colors.

The command palette opens with Command+E on macOS or Ctrl+E on other platforms, including from the startup entrance; the search-shaped button at the top of the sidebar opens the same panel and shows the platform shortcut on its right. It uses the public command plugin to search localized page names and English aliases, navigate to pages and open Settings. Gallery clears the query on each opening and closes the palette after activation. Settings → General offers persisted command-palette preferences for automatic ABC selection and showing results on opening or after a search. On macOS, when enabled, it requests ABC while searching and restores the preceding input source on dismissal, preserving a different source manually selected while the palette was open. Shortcuts stay within the window and wait behind other modal surfaces. Search and navigation remain in memory.

The **Plugins / Code** page independently demonstrates retained read-only highlighting for common languages and plain text, with selectable samples and source-copy buttons.

The **Plugins / Chat** page presents a static conversation with mixed execution blocks, a Markdown answer and a sample change summary. Successful execution folds behind an elapsed-time divider; details, response copying and sample diff review remain interactive. The bounded conversation viewport and pinned composer demonstrate attachment and model/effort controls without sending messages, simulating a timeline, accessing files or contacting a model. `TestNativeChat` captures static running, completed and failed fixtures in both themes, including a narrow Chinese layout; pointer, input-method and assistive-technology behavior still needs manual review.

The **Plugins / Markdown** page loads its [test document](../../source/resources/markdown.md) from the application resource directory and caches the parsed result. The fixture covers local images, missing-image fallbacks, text formatting, collections and custom code-block views. It reuses the bundled avatar image and works from both the source tree and packaged resources.

The **Desktop / Tray** page explicitly enables a MyGo tray icon and a small native notes window composed with Onevra controls. Rendering or navigating to the page alone creates no native resources. Once enabled, the tray survives page navigation; disabling it or closing Gallery destroys its icon and auxiliary window. The note remains in gallery-owned memory across hide/show and disable/enable cycles. The auxiliary window hides on close or blur without changing the main window's normal close-to-quit behavior. Platform requirements and interaction review are covered in the [development guide](../build.md#tray-example).

The **Desktop / System notifications** page sends native notifications only after an explicit action, using MyGo directly. Clicking a notification restores Gallery to that page. The gallery owns permission feedback and pending delivery, and withdraws its demo notification when replaced or closed. See [notification review](../build.md#notification-example) for platform requirements.

The macOS-only **Desktop / Dock menu** page installs application-wide Dock shortcuts explicitly through MyGo. Actions target the owning Gallery rather than the focused window supplied by a menu callback. Disabling the demo or closing Gallery restores the previous Dock menu unless another owner has replaced it. The system's standard Dock items and application menu are unchanged.

The Terminal plugin page automatically opens the user's default login shell on first entry, filling the content area below the titlebar without gallery padding or demonstration controls. MyGo owns shell selection, the pseudo-terminal, emulation and input; the gallery owns asynchronous native-library loading, retains the session across navigation and closes it with the window. Ordinary headless views do not start a shell or load the native library; native review exercises the real shell.

Packaging and native-library path adaptation belong to the gallery application, not the library. Startup selects the bundled Terminal library before the page can load it, without forcing eager native-library initialization. Build commands and distribution limitations are maintained in the [development guide](../build.md#app-bundles).

The settings toolbar action opens a Onevra Dialog over the current page, preserving navigation and sidebar state. On macOS, the application menu also provides Settings… with Command+,; it targets the main Gallery window even when another window is focused, restores a hidden or minimized window, and leaves the startup entrance when necessary. It hosts the public Settings component with application-defined categories and controls. Its grouped notification template keeps edits in memory and does not send notifications; the appearance section uses the same persisted theme preference as the toolbar. Search includes settings across all categories. Narrow windows replace the settings sidebar with a category selector. The application owns the dialog and persistence rather than adding settings or routing policy to Shell.

## Interface language

Gallery offers English, Simplified Chinese and Follow system in Settings → General. The preference lives in `config.yaml` alongside appearance and applies immediately to application-built content, component labels, Shell controls and the auxiliary notes window. Following the system resolves MyGo's locale at startup; unsupported languages, including Traditional Chinese, fall back to English. The disk-free example path defaults to English for deterministic review.

The application embeds matching YAML message catalogs and resolves them with go-i18n. Stable catalog IDs identify translations, independently of English copy, route IDs, widget keys, option values and persisted state. Existing demonstration metadata resolves through the English catalog; static interface text uses message IDs directly. Views read translations during each build, so changing language preserves drafts, selection, dialog state and navigation. Command search accepts English names and their translations; settings search uses localized metadata. Public components receive application-owned localization through the build scope described in [Components](components.md#localization).

Keep message IDs stable when editing English copy, translate complete messages and preserve format placeholders. Tests check catalog parity, explicit translation calls, formatting arguments and language-switch behavior. Component display names are localized; API identifiers, icon identifiers, filenames and editable demonstration content remain unchanged. Application-owned Dock, tray, context and toolbar action menus follow the selected language; installed menus update without losing their callbacks or ownership. The macOS application menu bar, standard OS items and strings internal to MyGo's own widgets and plugins remain unchanged. The Markdown fixture is document content; its surrounding controls use the interface language. Native review must cover both languages, narrow layouts, focus and input methods; headless tests cannot establish platform text fidelity.

## Component review

The read-only **Component status** page and startup console reminders share the same code-owned decisions. The page separates excluded components, replacements (including variants of one internal component), remaining MyGo examples, newly discovered entries without examples and retained composition primitives. Groups use name-only grids and empty groups are hidden. Replacements are grouped under the owning Onevra component, with the MyGo names it replaces. These are maintenance decisions and gallery coverage, not an audit of every application call site or of MyGo's transitive implementation.

The gallery's generation step scans the resolved MyGo module's UI source for exported free functions taking a context first, across platform files and including generic constructors. Base constructors and tests are omitted. `Menu` and `ContextMenu` are explicitly retained as direct MyGo native APIs, not pending Onevra implementations. All MyGo plugins are used directly rather than reimplemented by Onevra. Catalog entries in the Plugins group automatically receive direct-use status, retain their demonstrations and do not generate pending replacement reminders. Method-based demonstrations and plugins are supplemented by the hand-built gallery catalog; the scanner does not discover arbitrary new methods or plugins. Generated names and source locations are checked in, so running the app needs neither a Go toolchain nor a module cache. After every MyGo upgrade, run `GOWORK=off go generate ./examples/gallery/internal/gallery` from `source/` and review the generated diff. Ordinary `go run`, `go build` and [Packer](../build.md#app-bundles) use the checked-in snapshot without running generation.

Record replacements or exclusions with their reasons in the decision map, not in the generated inventory. Both remove the upstream example and reminder without affecting the internal component's own demonstration. New entries remain visible for review, do not create synthetic examples and do not block builds. No decisions are made interactively or persisted in user settings.

## Verification approach

Ordinary tests do not open windows. The opt-in native smoke test runs the actual MyGo event loop with temporary user data and captures light, dark and narrow views, including the settings dialog. Native bounds assertions check that opening settings preserves window geometry. Headless tests verify sidebar width limits and double-click reset; the native pointer path requires manual review. See [native review](../build.md#native-review) for the command and manual checks.

Content captures establish rendering but omit OS-composited background blur. Review blending in a live window over a contrasting backdrop; a content capture alone cannot prove it works. Keyboard interaction, accessibility and platform-specific window behavior also require native review rather than screenshot assertions.
