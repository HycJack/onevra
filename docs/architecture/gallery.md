# Gallery design

The gallery is a standalone example and a native review surface for the public components and icons. It must remain runnable without any consumer application.

## Separation from the library

The [entry point](../../source/examples/gallery/main.go) owns application startup, appearance selection and shutdown. The [internal gallery](../../source/examples/gallery/internal/gallery/gallery.go) owns demonstration content and in-memory state. Neither is part of the public component API.

Examples should demonstrate ordinary consumer integration, not introduce gallery-only behavior into components. The entry point places application data in `~/.oneo/onevra`. The gallery restores window size and position, sidebar width and expansion state, and the selected navigation item from `state.yaml`, and saves them on normal window close or application quit. Selection uses named routes rather than catalog indices; unknown routes and unreadable state fall back to defaults. Restored windows are kept within a connected display's work area where minimum sizes allow. Interactive demo values stay in memory, and no user content is persisted. Only the YAML filenames are read; existing JSON files can be renamed to `.yaml` to retain their values, since JSON syntax is valid YAML. Application preferences live separately in `config.yaml`, shared by the sidebar theme menu and future settings UI. The theme defaults to System; menu choices apply immediately and are saved immediately. An explicit `-theme` launch argument temporarily overrides the saved preference without rewriting it. Missing or invalid configuration falls back to System, with read and save errors logged. The disk-free `Gallery.New` path keeps component examples and native tests isolated from real user settings. Its grouped sidebar navigates between Onevra demonstrations, a Lucide icon library with icon-only outline buttons that copy their names and MyGo's remaining built-in widgets. The Components group exercises the public `components` package on interactive pages, grouping related controls while keeping state isolated between examples and from the upstream catalog. Preview layout follows the component: Text and Collapsible variants have separate canvases with muted, regular-weight descriptions above them; NativeSelect has its own canvas below the custom Select variants; other component variants share a canvas and wrap horizontally. Component names sit outside the canvas; descriptions inside it also use muted, regular-weight text. Rows remain appropriate inside a component, such as a radio group or tab list. Onevra previews do not include disabled-state demonstrations; disabled behavior remains covered by automated tests. MyGo entries are grouped by type and open separate control-only pages, without source listings or tutorial prose. State and usage variants remain interactive where enabled, with independent in-memory state per page and variant. The upstream examples omit direct-use primitives and native menus, as well as components recorded as replaced or excluded in the [component decisions](../../source/examples/gallery/internal/gallery/mygo_review.go); supporting controls use Onevra equivalents where available. Unstyled Base APIs remain building blocks rather than a duplicate widget catalog. The exhaustive icon catalog is generated alongside the Lucide assets by [lucidegen](../build.md#updating-lucide-icons). It belongs only to the gallery and references public named accessors; ordinary library consumers retain no runtime registry. MyGo's virtualized grid builds visible icons on demand. The Shell demonstration also shows sample icons at multiple sizes and inherited text colors.

The Terminal plugin page automatically opens the user's default login shell on first entry, filling the content area below the titlebar without gallery padding or demonstration controls. MyGo owns shell selection, the pseudo-terminal, emulation and input; the gallery owns asynchronous native-library loading, retains the session across navigation and closes it with the window. Ordinary headless views do not start a shell or load the native library; native review exercises the real shell.

Packaging and native-library path adaptation belong to the gallery application, not the library. Startup selects the bundled Terminal library before the page can load it, without forcing eager native-library initialization. Build commands and distribution limitations are maintained in the [development guide](../build.md#app-bundles).

## Component review

The read-only **Component status** page and startup console reminders share the same code-owned decisions. The page separates excluded components, replacements (including variants of one internal component), remaining MyGo examples, newly discovered entries without examples and retained composition primitives. Groups use name-only grids and empty groups are hidden. Replacements are grouped under the owning Onevra component, with the MyGo names it replaces. These are maintenance decisions and gallery coverage, not an audit of every application call site or of MyGo's transitive implementation.

The gallery's generation step scans the resolved MyGo module's UI source for exported free functions taking a context first, across platform files and including generic constructors. Base constructors and tests are omitted. `Menu` and `ContextMenu` are explicitly retained as direct MyGo native APIs, not pending Onevra implementations. Method-based demonstrations and plugins are supplemented by the hand-built gallery catalog; the scanner does not discover arbitrary new methods or plugins. Generated names and source locations are checked in, so running the app needs neither a Go toolchain nor a module cache. Refresh generation after dependency changes; ordinary `go run` and `go build` use the checked-in snapshot, while [Packer](../build.md#app-bundles) refreshes it before compilation.

Record replacements or exclusions with their reasons in the decision map, not in the generated inventory. Both remove the upstream example and reminder without affecting the internal component's own demonstration. New entries remain visible for review, do not create synthetic examples and do not block builds. No decisions are made interactively or persisted in user settings.

## Verification approach

Ordinary tests do not open windows. The opt-in native smoke test runs the actual MyGo event loop with temporary user data and captures light, dark, narrow and replacement-page views. Native bounds assertions check that replacement pages preserve window geometry. Headless tests verify sidebar width limits and double-click reset; the native pointer path requires manual review. See [native review](../build.md#native-review) for the command and manual checks.

Content captures establish rendering but omit OS-composited background blur. Review blending in a live window over a contrasting backdrop; a content capture alone cannot prove it works. Keyboard interaction, accessibility and platform-specific window behavior also require native review rather than screenshot assertions.
