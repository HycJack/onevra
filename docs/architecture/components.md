# Component design

The public [shell package](../../source/shell/doc.go) owns native window presentation and a replaceable page container, not an application framework. The [components package](../../source/components/doc.go) provides common controls independently of Shell. Shell also provides icon buttons for titlebar and toolbar actions. Both packages compose MyGo directly. Shell reuses the common Icon component; components remain independent of Shell.

Common controls expose at most one visual variant axis, such as button style. Each control has one theme-scaled standard size rather than a separate size enumeration. Interaction and value states are not visual variants.

## Composition and ownership

Shell creates and configures the MyGo window because transparency, title-bar style and traffic-light placement must be set at creation time. It exposes MyGo's original handle for application events and lifecycle operations, rather than introducing a second event or shutdown system. Applications should not replace the window's content behind Shell.

Applications own business state, localized text, actions and page selection. The reusable [Sidebar](../../source/components/sidebar.go) composes grouped navigation independently of Shell; it supplies item appearance, while applications handle activation and scrolling and Shell owns the window's sidebar geometry. Content builders and Shell state changes run synchronously on the UI thread; builders must not launch repeated background work during rendering. MyGo's value-based Element handles belong to the current build pass, not application state. Use a bound MyGo Handle for identity or geometry queries between builds. Shell owns only presentation state, does not persist it, and uses MyGo's rendering, layout and input systems.

Components read the frame theme and style their own elements; they must not call `Context.SetTheme`, which also resets the window root's appearance. Only application-level theme installation owns that operation. Collection controls compose their own rows and component-level selection/navigation on MyGo's input and focus APIs. Virtualized collections reuse non-selecting MyGo list and grid containers for scrolling and layout, rather than copying its layout engine or overriding its styled row theme. Their application-owned state is defined in the [collection API](../../source/components/list.go). Public role, selection, level and active-descendant metadata describe the rows, but this composition does not claim full parity with MyGo's private collection accessibility actions; native assistive-technology review is still required.

For basic usage, see the [README](../../README.md#basic-usage); public contracts and defaults belong to the [API source](../../source/shell/shell.go).

## Page container and layout

The page container reserves space for system window controls and overlays a transparent draggable header with a Lucide sidebar control. The toggle keeps additional clearance from macOS traffic lights. Its default page contains a collapsible left sidebar and a flexible main region. Both regions and their application-built content extend to the top of the window behind the header. Applications own the top inset: use Shell's frame-aware header height to keep interactive content clear while painting backgrounds through the titlebar area. The header retains window dragging and control interaction above the body. Applications can supply the leading main-content titlebar area for a title, breadcrumbs or actions. It aligns with the main surface, clears the sidebar toggle when collapsed, and clips within the remaining native-control safe area.

The optional left bottom toolbar remains beneath the sidebar body and disappears with the sidebar or on replacement pages. It composes MyGo's toolbar, retaining its focus navigation and overflow behavior. Applications supply actions and labels; the reusable [icon button](../../source/shell/icon_button.go) uses MyGo button semantics with transparent resting faces and translucent text-color interaction feedback.

The left sidebar keeps its content at the full sidebar width while its visible slice animates, so the opaque main region appears to cover or uncover it without resizing the window. A thin separator overlays the main region's left edge, takes no layout space and disappears when the sidebar is fully closed. Its overlaid drag handle spans the full window height, taking precedence over window dragging at the separator, and supports keyboard arrow adjustment; double-clicking restores the application-configured default width. Applications can bound resizing with minimum and maximum widths. Shell retains the chosen width across toggles and page changes and removes the handle while collapsed or transitioning. The main region takes the remaining space rather than reserving a fixed share of the window. Narrow layouts only constrain the sidebar to keep its resize handle inside the viewport, without discarding the chosen width; widening the window restores it.

A replacement page occupies the full window behind the shared floating header, with the same application-owned inset and hides the default page's titlebar content and sidebar controls. Returning restores the previous sidebar state without changing window geometry. Shell provides this switching mechanism, not a settings implementation or business router.

MyGo's animation values drive the sidebar reveal, without a separate timer or animation loop. Reversing a toggle mid-animation continues from the current visible width; Reduced Motion skips intermediate geometry.

## Dialog composition

Dialog composes MyGo overlay, modal focus scope and transition primitives rather than a separate modal manager. Applications own open state and build layers in back-to-front order; nested dialogs retain the underlying page. Each layer controls backdrop and Escape dismissal independently. AlertDialog composes the same surface and Onevra buttons, emitting a frame-local result instead of blocking the UI thread. Applications own localized labels, retain results when needed and provide scrolling for long dialog pages. MyGo owns focus trapping, restoration and reduced-motion behavior.

## Native appearance

MyGo and the operating system provide native window interaction semantics. On Windows, Shell uses MyGo's frameless window and composes rounded toolbar-style minimize, maximize/restore and close buttons in the shared header, including replacement pages. Labels are application-localizable; close requests retain MyGo's cancellable application lifecycle. Maximize/restore follows the actual window state. Shell applies Onevra's built-in light and dark themes (see the [theme package](../../source/theme/doc.go)) through MyGo's own theme mechanism, so every MyGo widget keeps working; there is no separate theme manager or custom window chrome. `ShellOptions.Appearance` selects `theme.Auto` (the default, follows the system appearance), `theme.Light` or `theme.Dark`. A pinned theme ignores later appearance changes, while window chrome still follows the operating system. These UI buttons do not implement Windows' native maximize-hover Snap Layouts flyout.

On macOS, a transparent native window and transparent UI root expose a blurred system material. The left sidebar preserves that material, adding a translucent blue-gray tint in dark mode. Main content and replacement pages remain opaque, extending behind the unpainted header. Windows and Linux retain an opaque theme background rather than claiming unverified blur support. On Windows, and in dark mode on Linux, the sidebar uses a contrasting theme surface through the header and bottom toolbar to distinguish it from main content.

Application builders can obscure the material by painting their own backgrounds. Preserve transparency through the window and sidebar when changing styling; content captures alone do not include the OS-composited blur.
